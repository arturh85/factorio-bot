# A search that ranks layouts by flow, and what its ranking gets wrong

2026-09-08. Branch `a-search-that-ranks-plans-by-flow`, off `a88308d1`. The
owner's question: *"we have so many goals and decisions in factorio, not sure
how we can decide at all, maybe genetic algorithms or some other stuff could
optimize the plan at the end ... or we make simulations, trying which layout /
prio maximizes achieved flow rate."* The ruling was a working prototype that
ran and produced a ranking, plus an honest account of what the ranking gets
wrong. Both are below, numbers first.

Everything here was measured on this branch's own debug binary. The four
planner baselines reproduce exactly on it before any of this landed:
`researched:automation` 176 / 21,784 · `producing:automation-science-pack:6`
316 / 22,457 · `producing:logistic-science-pack:6` 441 / 47,478 ·
`gathered:crude-oil` (explored map) 2,115 / 317,283. The search touches no
planning path, and they are unchanged after.

## 1. What was built

`factorio-bot search --world <dump>` (`app/src-tauri/src/cli/search.rs`, over
`crates/planner/src/search.rs`) ranks **layouts** -- named lists of blueprint
entities -- by the iron plates per minute the flow graph says they would
sustain, with what they cost in plates to stand up beside it. A candidate is
either a fixture from `scripts/rcontest.lua` or a block generated by
`search::ore_to_plate(drills, furnaces)` in the **exact geometry of the
measured `OreToPlateThree` fixture** -- `gen-3x2` decodes to that fixture entity
for entity, and a test says so. That is what makes the model's number
checkable: the fixture has a live rate in the record.

Scoring one candidate is: a fresh `EntityGraph` holding the real ore patch
nearest spawn (940 tiles off the seed-31337 dump) plus the block, sited so the
most drill tiles stand on ore; `connect()`; `FlowGraph::sustained_production_
rates()`. **0.5-1.5 ms per candidate**, printed beside every row; the 164 MB
dump loads once, in about a second. The plates to build it are expanded
through the recipe table (`raw_cost`), never typed.

`core::blueprint::encode` is the inverse of `decode` and is new: it is what
lets a *generated* layout be handed to `goal.built` and to a script, so the
block measured in the game is byte for byte the block that was scored.
`scripts/rate_block.lua` + `tools/rate_block.sh NAME <instance>` are the live
half: one fresh map per variant (`--seed 31337 --new`), one isolated headless
instance each (`workspace/headless-{a,b,c,d}.toml`), 10x, a 30,000-tick window
in 3,000-tick marks, furnaces drained as the run goes so the number is a rate
and not a storage count -- the apparatus of `rate_three_drills.lua`,
generalised. It reports the cumulative rate and a **steady-state** rate over
the last third of the window, for the reason in section 3.

There is a second, slower tier. `--plan` also plans `goal.built` at the
chosen anchor on the t=0 world with the four-bot roster, which prices what the
block costs to **stand up from nothing**: `gen-3x2` is 208 actions and 22,642
ticks (6:17 of game time), `gen-5x2` 175 / 24,969. That tier is **0.8-1.0 s
per candidate** against the flow tier's millisecond, and it is what a
"which block next" search would have to pay.

## 2. Why enumeration and not a genetic algorithm

Because the measured cost per candidate is a millisecond, and a second at
the plan tier. The parametric
family is `drills x furnaces`; a 6x6 sweep with its unfuelled twins is 72
evaluations and finishes in well under a second after the load. A population
search over a space this size ranks noise against an exhaustive answer. The
owner's suggestion is the right tool the day the space is combinatorial --
siting, orientation, belt topology, which block *next* -- and the cost figure
to justify it will be measurable then the same way. Today the simple thing
answers the question.

## 3. The ranking, and the calibration behind it

`search --world map-31337-explored-with-categories.json --drills 1-6
--furnaces 1-6 --rcontest scripts/rcontest.lua`, plates per minute sustained:

```
candidate   ore/min  plates/min  iron  payback   note
gen-6x5        90.0       90.0    190    2.1m    5 furnaces bind at 93.8; drills at 90
gen-6x6        90.0       90.0    209    2.3m
gen-5x4        75.0       75.0    160    2.1m    exactly balanced: 5 x 15 = 4 x 18.75
gen-6x4        90.0       75.0    172    2.3m
gen-5x5        75.0       75.0    178    2.4m
gen-4x4        60.0       60.0    148    2.5m
gen-4x3        60.0       56.2    130    2.3m
...
gen-3x2        45.0       37.5     99    2.6m    the measured fixture
gen-2x2        30.0       30.0     87    2.9m    = OreToPlateTee, translated
...
gen-6x1        90.0       18.8    116    6.2m    one furnace: the output-capped corner
gen-1x6        15.0       15.0    149    9.9m    one drill: the starved corner
```

The sweep separates the corners the way the arithmetic says it should: with
one furnace every column reads 18.8 whatever the drills; with one drill every
row reads 15.0 whatever the furnaces; the diagonal climbs. Payback (plates to
build over plates per minute) is the compounding number the owner asked for,
and it is flattest along the balanced diagonal: `gen-5x4` pays for itself in
2.1 minutes, `gen-1x6` in 9.9.

**Then four of those rows were built in the game, on four fresh maps.**

|---|---:|---:|---:|---:|
| `gen-5x4` (balanced, top pick) | 75.0 | 70.3 | **75.2** | 1.003 |
| `gen-4x1` (output-capped) | 18.75 | 18.2 | **18.8** | 1.002 |
| `gen-1x4` (starved) | 15.0 | 14.5 | **14.8** | 0.987 |
| `gen-3x2-nocoal` (control) | 37.5 | **0.0** | **0.0** | -- |

And the two the record already had, from the peer sessions' runs of the same
block (`2026-09-07-the-block-was-drill-limited.md`), cumulative over 30k:
`gen-2x2` = `OreToPlateTee` 28.7 against 30.0 (model / game 1.045), `gen-3x2`
= `OreToPlateThree` 36.2 against 37.5 (1.036).

## 4. The bias, quantified: uniform where it exists, and where it does not it is total

The brief's most important question was whether the flow graph's idleness
over-prediction -- +16% to +23% on the world-record base -- is *uniform*
(ranks still correct) or *differential* (ranks inverted). On this family the
answer has two parts, and they are different in kind.

**Where the model has a number, the bias is a ramp, not idleness, and it is
uniform.** Every cumulative figure sits 3-7% under the model (1.033 to 1.067,
model over game) and every steady-state figure sits within 1.3% (0.987 to
1.003). The 5x4 curve shows why: 33.6/min over the
first 3,000 ticks while the belt fills, 74.4 over the last 3,000. A whole-base
balance is a steady-state model and the record's earlier fixture figures
(28.7, 36.2) are cumulative-with-ramp figures, so their 3.6-4.5% "over-
prediction" is mostly the first 3,000 ticks of a 30,000-tick window. Against
the steady state the balance is right on the balanced block, the drill-limited
block and the furnace-limited block alike, which is exactly the uniform case:
the ordering survives. The world-record base's idleness -- 194 drills at
`waiting_for_space_in_destination`, 21.7% of assemblers `full_output` -- does
not appear here because nothing here is back-pressured: the furnaces are
drained and the belt never fills. That is a fact about *this* family. The
moment a searched layout has a real downstream (a chest that fills, a science
block that consumes slower than the smelter makes), the world-record error
term returns, and nothing measured tonight says how it is distributed across
layouts. **Uniform on burner blocks with a drain is what was shown; uniform in
general was not.**

**Where the model has no number, the failure is not a bias at all.** The
unfuelled twin scores 37.5 in the model and makes zero plates in the game.
The model cannot see fuel (a burner's coal is not a recipe ingredient, and
`the_ground_is_not_a_recipe` is deliberate), so a search over layouts that
differ in fuelling would rank a dead block equal to a live one. That is
differential in the worst way -- it is not off by a factor, it is off by the
whole answer -- and it is why the CLI prints every generated block beside its
`-nocoal` twin: the tie is the finding, and a reader should see it rather than
be told about it.

## 5. What this ranking gets wrong -- the limits, as limits

- **A block nothing mines into scores zero, and zero is not a score.** The
  flow walk roots only at drills on ore and offshore pumps. `TJunctionSmelter`,
  `TwoRowSmelter`, `SaturatedSmelter`, `ElectricSmelter`, `FurnaceLine`,
  `SmeltRow24` and `StarterSteamEngineBoiler` are chest- or hand-fed and the
  table lists them under `unreached -- the model has NO number for these`.
  Ranking them last would have been a lie; excluding them means the search
  cannot compare a drilled block against a fed block at all.
- **A furnace with no output side scores zero plates.** The walk records a
  producer's output on an edge *leaving* it, so `OreToPlateTee` and
  `OreToPlateThree` as shipped -- 30 and 45 ore/min in, no takeoff arm --
  score 0.0 plates. That happens to be the game's own long-run answer (the
  result slots fill at 200 and the block stops), reached for an unrelated
  reason. The generated family adds a takeoff arm per furnace, which is the
  measuring apparatus made into entities and **not a design**: a burner arm
  that carries only plates has no fuel and stops, as the record already says.
  `ore_to_plate_with(..., drained = false)` reproduces the fixture exactly.
- **Fuel is invisible.** Section 4. The `-nocoal` twin is a control, and a
  search must never be run over a family that varies in fuelling until the
  model can see it.
- **A multi-output machine is scored per product with an independent outlet
  cap**, and the game stops the whole machine when any one output backs up.
  Verified by reading `nameplate_lines` and `balance`; not measured, because
  in this build the flow walk never reaches a refinery at all -- the pipe rule
  wires pipes to pipes, tanks, pipe-to-ground and boilers, and an assembling
  machine is not on the list (`input_provenance`'s doc, and the peer session
  adding fluidbox fields is exactly the work that will change it). So today an
  oil layout scores `unreached`, and the day pipes reach refineries it will
  score at nameplate on the products that still drain while the game reads
  zero. `Layout::multi_output_machines` marks such a layout `UNSCOREABLE` from
  the prototype and recipe tables (every recipe in every category the machine
  accepts yields more than one product) and the CLI refuses to rank it; the
  guard is in place before the number it guards against can appear. Run on
  a one-refinery blueprint the table reads `multi-output machine(s)
  oil-refinery (can run advanced-oil-processing, coal-liquefaction) would be
  scored per product; the game stops the whole machine` -- the two recipes
  named off the dump's own tables, with `basic-oil-processing` and
  `simple-coal-liquefaction` (one product each) correctly not among them.
  The first version of that guard required *every* recipe in the category to
  be multi-output and so could never fire on a refinery; it was checked
  against the dump before it shipped, and replaced.
- **Beacon lanes are not a term.** `EntityGraph::add`'s whitelist excludes
  beacons, so a search optimising density would pave the lanes the owner's
  standing instruction protects, and nothing here would object. The generated
  family has fixed pitch and does not vary density, so the search cannot
  currently make that mistake -- by construction of the family, not by any
  guard. A family that varies pitch needs the lane reserved as a constraint
  first.
- **The idleness term is unmeasured off this family.** Section 4's second
  paragraph. A ranking of layouts with real downstream consumers inherits the
  world-record error and its distribution is unknown.
- **Siting is the search's own, not the planner's.** `search::site` puts the
  most drill tiles on the nearest patch; `goal.built`'s `search_site` chose
  anchors one tile off from it in every live run (e.g. (-20,-21) against
  (-20,-15) for `gen-5x4`) and covered every drill tile too. Same patch, same
  coverage, different anchor; the rates agree, so this did not matter tonight,
  and it is a second siting story that should not exist for long.

## 6. What survived contact, and what did not

- **Verified against the brief**: `nameplate_lines` pushes one line per
  product and `balance` caps each independently (premise 3); the whitelist
  excludes beacons (premise 4); a per-machine duty cycle is ruled out in the
  code's own doc and tests (premise 2). The baselines reproduce.
- **Not as the brief had it**: the "+16% to +23%, unbounded" idleness term is
  the *pre-balance* figure. `sustained_production_rates` landed on 2026-09-07
  and takes the record base's mean absolute log error from 0.298 to 0.141 --
  `a-machine-standing-still.md` and `the-mall-was-not-the-problem.md`. The
  brief's premise 1 was a day stale when written, which is the brief's own
  warning about itself coming true.
- **Found on the way**: `insert_to_inventory` on a narrow block walked the
  bot to a tile the RCON layer refuses as "inside transport-belt" and killed a
  run before it measured anything. A character can stand on a belt; the check
  is stricter than the game. `crates/core/src/factorio/` was off limits, so the
  script parks the bot on open ground north of the drills first and `pcall`s
  each charge, counting what it could not fuel. Handed over, not fixed.
- **A near-exact match was checked before it was believed**: 75.2 against
  75.0 on a block whose drills and furnaces are both *exactly* 75/min by
  prototype arithmetic (5 x 0.25/s; 4 x 1/3.2 s) is the case where a
  deterministic machine with a buffered belt has nothing to be idle on. It is
  not evidence the model is right in general; it is evidence the model is
  right where the world-record base's error term is absent.

## 7. How the tests were checked

Nine unit tests in `search.rs` and two in the CLI. Six mutations, each
applied alone and each restored with a `touch` (the `cp -p` trap): the
corner belt turned east instead of south -- four tests red, including both
rate tests, because the ore never reaches the furnaces; the drill footprint
shifted a tile -- the footprint test red; the rank order inverted -- the rank
test red; the multi-output threshold raised -- the guard test red; the
takeoff arm faced the wrong way -- three tests red, because a furnace with no
edge leaving it scores no plates; `encode` writing every direction as 0 --
the round-trip test red. Restored: 9 of 9 green, then planner 948 and core
649 lib tests green with the module in, and clippy clean on planner, core and
the CLI crate with `--deny warnings`.
